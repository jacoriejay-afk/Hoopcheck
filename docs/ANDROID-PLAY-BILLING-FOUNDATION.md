The Android screen deliberately remains consumption-only pending owner and storefront review. The proposed catalog uses two subscription IDs with three base plans each, matching existing USD reference amounts; these IDs are proposed, not verified Play Console products. No offers/trials approved or enabled. Keep iOS/Stripe unchanged. Review actual localized Google prices at purchase time.
 
Implemented: proposed catalog/role policy, conservative server-response interpreter with account/test environment checks, expiry and acknowledgment distinction, blocking replacement chains and unapproved offers, Android-specific membership UI without Apple controls, synthetic regression tests. Interpreter MUST ONLY receive authenticated Google Developer API responses; not a client trust boundary. Never use its result to grant access without persistence, ownership, acknowledgment, reconciliation and authorization. No Play provider added to effective entitlement types yet.
 
Remaining implementation (separate reviewed work): current supported Play Billing Library native bridge and Android compile; approved Play Console catalog; server OAuth service account and scoped package; server-issued HMAC obfuscated account IDs; purchases.subscriptionsv2.get with pinned package and bounded requests; secure token encryption/hash, immutable owner binding, transaction/linked token fencing, deduplicated acknowledgement, RTDN and periodic reconciliation, expiry/refunds/revocation, stale-state handling, sandbox isolation, cross-provider entitlement SQL and tests, trial policy/first-payer history, deletion/retention, Android signed license testing and actual Play policy/store declarations. No environment or migration changes authorized.

## Purchase credential vault primitive
Server-only lib/server/play/token-vault.ts uses AES-256-GCM with random 96-bit nonces and authenticated owner, package, environment and fingerprint context. The independent keyed HMAC index is owner-independent for future immutable uniqueness enforcement. Two distinct 32-byte keys are required; never reuse the account-binding key. Ciphertext cannot be moved across owners/environments or paired with another fingerprint. Four synthetic tests cover encryption, corruption, substitution and bounded inputs. This is not durable storage: no table or repository adapter exists. A future transaction must atomically bind a unique environment/package/fingerprint to its first verified owner; deny foreign ownership, fence concurrent writes, preserve deletion holds and acknowledge only after durable verified ownership. Key versioning/rotation, retention, recovery, and database access policies must be approved before integration. No raw tokens in logs, public APIs or client storage. No acknowledgment, entitlement change or migration executed.

## Durable test ownership candidate
The standalone, unapplied candidate supabase/candidates/android_play_purchase_ledger.sql defines a private test-only claim table and invoker function. It is NOT a migration; never apply it to a hosted project or expose the schema. Composite primary key prevents duplicate token claims, first owner and encrypted envelope are immutable, same-owner retries are idempotent and competing owners or changed product/plan are rejected. Explicit RLS and grants deny clients and prevent the service role from updating/deleting claims. The disposable PostgreSQL 17 workflow checks these conditions and races two owners. No live credential or purchase data. This is a candidate ledger, not an application repository: actual Auth/deletion freeze, reviewed schema/FK and erasure policy, transactional entitlement fulfillment and integration adapter remain required. Google recommends verifying purchase and fulfilling entitlement before acknowledgment (https://developer.android.com/google/play/billing/integrate); do not acknowledge purchases until the application can durably fulfill and reconcile them. No acknowledgment endpoint or public purchase flow is enabled. Production ledger reconciliation remains separate.

## Fenced lifecycle rehearsal
Unapplied android_play_lifecycle.sql extends only the disposable purchase-claim schema with a generation counter, a 60-second refresh lease, and advisory test observations. New refresh invalidates old observations; older, duplicate, expired-lease and foreign-owner completions cannot overwrite the newest generation. A completed observation expires after 30 minutes, or earlier at subscription expiry. Pending acknowledgment is distinguishable from eligible-for-reconciliation. This is deliberately not a grant, real subscription state adapter or live scheduler; Google RTDN, purchase replacement chains, durable fulfillment, deletion handling, provider acknowledgement and existing entitlement integration remain separately required. The isolated PG17 workflow now also checks refresh fencing, owner scope, invalid expiry, stale evidence and in-flight fail-closed behavior. Lease and freshness durations are conservative candidate defaults for review, not a claim of provider policy.

## Internal native purchase and recovery operations
PlayPurchaseOperations.kt compiles with the Android module and contains the native Google Play launch and recovery calls, but intentionally has no Expo-exported or app-callable payment entry point. Full-price plan matching requires the exact localized price/currency, supported recurring period, no offer or installment, no duplicate plan, foreground activity and a fresh quote. The provider flow receives the obfuscated account ID. Recovery queries subscriptions and filters exact account IDs, known single products, bounded tokens and PURCHASED state; PENDING is counted separately. No credential logging, acknowledgment or entitlement grant. Native launch success is only a UI launch response. Before exposing this code, implement a single-flight coordinator that binds verified server intent to fresh ProductDetails, active account, session generation, callback/timeout and server verification; wire restore and foreground recovery, discard late responses, and verify the signed sandbox. Current tests are static contracts plus the existing Gradle compile gate, not physical purchase tests. See https://developer.android.com/google/play/billing/integrate .

## Account-scoped purchase coordinator candidate
Unwired createPlayPurchaseCoordinator in mobile source validates an exact test-only server intent, localized reviewed quote, allowed role, fresh expiry (at most 60 seconds), current bearer/session and account generation. ## Provider acknowledgment and RTDN contracts
Unwired acknowledgment.ts validates test receipt, immutable token fingerprint, verified product/plan and expiry, and rechecks durable fulfillment before a bounded POST to Google's documented subscription acknowledgment path. It requires explicit dependency injection (no default fetch, OAuth or DB adapter); a successful response only requests re-verification. Synthetic receipt must never authorize a real provider write. rtdn.ts parses an already independently authenticated Pub/Sub push for the configured subscription and exact package; validated subscription and voided subscription notices only schedule re-verification, never grant access. No public route, Pub/Sub OIDC authentication, durable queue/dedupe or worker exists yet. Unknown subscription event types trigger fresh verification, not policy inference. Five synthetic tests cover exact request, missing/conflicting receipt, errors, and malformed/foreign notifications. Current Google references: https://developers.google.com/android-publisher/api-ref/rest/v3/purchases.subscriptions/acknowledge and https://developer.android.com/google/play/billing/rtdn-reference . Actual provider calls remain disabled until live fulfillment is accepted.
