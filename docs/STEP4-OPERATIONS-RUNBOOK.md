# Step 4: operational release readiness

Refs #1139, #1137, #1138, #1006, #1073 and #1075. This is a review-only operational runbook. No production, hosted database, EAS, store, billing or paid service actions are authorized.

## Launch control
Pin the candidate commit, native build identifiers, environment and observation time. Run the release-evidence checker against a private, redacted evidence manifest. Never store access tokens, raw customer data, payment details or signed media in evidence. A passing manifest is a structural check, not independent verification or release approval. A reviewer must open every evidence link, check exact source/build, coverage and outcome. Reuse Owner HQ release observations for aggregate regression signals; a quiet metric is not proof of readiness.

## Incident and rollback
1. Record UTC time, affected platform, exact deployed version, symptoms and scope. Categorize P0 (auth/security/data loss/billing), P1 (major function unavailable), P2 (degraded/noncritical). Hold rollout on P0/P1.
2. Preserve redacted logs and evidence; never paste tokens or customer records. Identify whether code, provider, configuration or database is implicated. Notify owner and designate a single incident coordinator.
3. Inventory existing emergency flags and their actual server enforcement. Only an approved operator may change an existing flag after recording previous value, scope, reason, expected impact, expiry/review time and rollback. Never disable authorization or moderation to restore functionality.
4. Before a rollback, check schema/API compatibility with old signed clients, migration reversibility and billing/webhook idempotency. Roll back code only if compatible; otherwise prefer an reviewed forward repair. Never restore a production database or reverse a destructive migration without separate authorization and rehearsed recovery.
5. Verify affected flows, monitor recovery and document timeline, root cause, follow-up and owner sign-off. No automatic production mutation.

## Backend hygiene and restore drill
- Inventory tables, views, functions, grants, RLS, indexes, storage policies, scheduled jobs, API dependencies and provider rights. Use source references, migration history and bounded catalog/statistics queries. Low traffic is not proof of disuse; retain unknown objects and legacy client dependencies. Do not delete or mutate production.
- Rehearse only on an isolated disposable full-schema database with synthetic records: capture schema/migration versions, seed representative users/roles and membership states, export and restore, compare counts and constraints, verify auth links, access denial, private storage references, billing/event deduplication and migration compatibility. Record elapsed recovery time and tested data-loss window; never claim an RPO/RTO from an unrun drill. Redact outputs; remove temporary data after rehearsal.
- A source audit or fixture does not prove hosted backup availability, actual recoverability or production parity.

## Smoke and reliability coverage
Use local or explicitly approved isolated endpoints only. Verify public routes and authorized private routes with synthetic accounts for each role/tier. Include signup/recovery, Owner HQ denial, feed/group/chat/report/block, media permission and interrupted upload retry, directory paging, billing sandbox and notification delivery. Negative cases: offline, provider timeout, duplicate submission, stale session, rate limits and cross-account access. Bound timeouts/concurrency; never stress production. Record statuses without request bodies, tokens or user identifiers. Native physical-device, signed links and store sandbox evidence are separate gates.

## Operations handoff
Track cost signals and notification/media provider delivery using existing telemetry, no new paid services. Unknown values remain unknown. Audit retention/expired-media cleanup with dry-run only; audit accessibility (VoiceOver/TalkBack, larger text, contrast, reduced motion), older OS compatibility and beta support escalation. Owner approval is required for rollout, deployment or store submission. All outstanding #1139 implementation gaps remain open until proven on the exact candidate.

Run `node scripts/step4-release-evidence.mjs --self-test` and `node scripts/step4-release-evidence.mjs /private/path/manifest.json <candidate-sha> <ios-build> <android-build>`. Obtain the three expected identifiers from the verified candidate and signed artifacts before opening the manifest. Required gates: ci, security, schema_restore, web_smoke, ios_signed, android_signed, billing, hosted_auth, privacy_fulfillment, external_providers, legal_approval, ios_native_capabilities, android_native_capabilities, combined_technical, operations. Native capability evidence is separate from general signed-device acceptance, and must match the corresponding platform build and exact candidate SHA. Combined technical evidence requires the final reconciled SHA, full applicable CI, web/native regressions and security review; prior individual PR checks are insufficient. `hosted_auth` requires real isolated hosted email confirmation, recovery and Google/Apple callback evidence as applicable; `privacy_fulfillment` requires actual synthetic-account deletion, export, revocation and retention checks in an isolated environment; `external_providers` requires authorized sandbox provider configuration and delivery evidence; `legal_approval` requires owner-approved current Terms, Privacy disclosures and retention requirements, not invented retention periods. Synthetic or mocked provider tests alone do not satisfy these gates. Earlier manifests missing these gates must remain on HOLD. Evidence must match the candidate SHA and signed build, be reviewed within seven days, and link to the HoopCheck repository. The checker does not verify remote links or sign-off authenticity.

## Final production and mobile acceptance

- Verify the QA candidate SHA and exact-head workflow results. Review the candidate against its merge base and confirm the frozen Build 16 ref and protected branches stayed outside the integration. Attach each test result and its reviewer to the release evidence.
- Exercise the read-only route smoke and bounded loopback burst on the production build with fixture configuration. The smoke covers both recovery entry points and anonymous denials for mobile bootstrap, Owner HQ, Ambassador HQ, and both review endpoints. Run authenticated role and tier fixtures, interrupted uploads, account switching, moderation, expired media and cache boundaries as separate checks.
- Obtain the reviewed schema baseline and ledger described in the [rehearsal preflight](appstore-schema-rehearsal-preflight.md). Record the disposable full-schema recovery result and reviewed rollback constraints before approving any migration.
- On separately authorized signed iOS and Android candidates, record fresh install and upgrade results, email and provider callbacks, permissions, foreground and background recovery, memory and cold start, poor network, notifications, Passport PDF/share cleanup, themes, assistive technology and supported OS versions. Record device, OS and build for each result.
- Reconcile approved sandbox billing evidence for trial, restoration, renewal, refund, cancellation and provider precedence. Confirm actual account deletion and export, approved retention, provider revocation, current Terms and Privacy disclosures and storefront declarations.
- Confirm the incident coordinator, support escalation, redacted crash signal, feature disablement and rollback triggers. Record the rollback-compatible known good release. Keep release on hold until each gate has current reviewed evidence and the owner authorizes rollout.

## Signed native capability acceptance (no new build authorization)
Use only signed artifacts whose source SHA matches the candidate; record build ID, OS, device model and observation time for each platform. For iOS verify Dynamic Island/Live Activities on supported hardware, Share Extension invocation and cancellation, Picture-in-Picture, universal links including cold launch, camera/mic/media permission denial and retry, push delivery, Passport PDF and share cleanup, background/foreground, offline recovery and account switching. For Android verify applicable PiP, share intent, app links, media permission denial/retry, push delivery, Passport PDF and share cleanup, background/foreground, offline recovery and account switching. Record platform-exclusive features as not applicable with rationale, not as passed. Unsupported or missing signed builds remain HOLD; do not substitute simulator or old-build results. See [consolidated Steps 1–4 tracker](steps-1-4-acceptance-tracker.md).
