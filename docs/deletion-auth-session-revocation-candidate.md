# Fenced session and refresh-token revocation candidate

The normal owner-bearer Auth global sign-out path remains preferred. The alternative scheduled-worker path is separately disabled in both application configuration and the private database policy. It matches the reviewed PG17 Auth catalog (session and refresh-token user types and cascading AMR/refresh foreign keys); it is version-specific internal database code, not a supported general-purpose Supabase Auth API. No hosted execution, credentials or activation. The candidate locks and verifies the exact frozen step-4 lease and active ban, rejects catalog drift and cross-owner token links, removes the owner's sessions and legacy refresh tokens atomically, and returns only a boolean. The existing confirmation RPC checks both tables. Unrelated owners are never targeted. A real isolated GoTrue test (refresh grant rejection, in-flight login races, stale JWT access, RLS and post-revocation catalog) is mandatory before activation. Already-issued JWTs are not cryptographically invalidated; the existing freeze/active-session checks remain required. A reviewed retention policy and actual-schema acceptance remain prerequisites.
